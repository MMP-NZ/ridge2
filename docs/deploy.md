# Deploying Ridge

## Where things stand

**Staging runs on Render, Singapore, with fictional data only.** Everything is defined in [`render.yaml`](../render.yaml).

**Production isn't decided.** `CLAUDE.md` locks customer data to NZ hosting, and Render has no NZ or Australian region. Until that decision changes (recorded in `docs/decisions.md`), no real roofer's customers go into Render. The alternative already researched is AWS `ap-southeast-6` (Auckland). The same image, bundles and database-role setup work there unchanged.

## What runs

| Render resource | What it is | Command |
|---|---|---|
| `ridge-staging-web` | Next.js server, with a 5 GB disk at `/var/data` for photos | `node server.js` |
| `ridge-staging-worker` | pg-boss background jobs: texts, follow-ups, Xero sync | `node dist/worker.mjs` |
| `ridge-staging-db` | Postgres 16 | — |

Both services build from the one `Dockerfile`. On the web service, `preDeployCommand: node dist/migrate.mjs` runs migrations after the build and before traffic moves, so a failed migration leaves the previous version serving.

Deploys trigger only once CI passes on `main` (`autoDeployTrigger: checksPass`). CI has a `deploy-rehearsal` job that runs the same build, bundles, migrations, worker and health check against a Postgres 16 whose owner isn't a superuser. If that job is green, the Render deploy has already been run once.

## First-time setup

These need the Render account holder.

1. **Create a Render workspace** and add a payment method. The worker and the disk can't run on free instances.
2. **Generate the encryption key** on your own machine. Keep a copy in your password manager, because a lost key means every stored Xero and Meta token has to be reconnected:
   ```bash
   openssl rand -hex 32
   ```
3. **Render dashboard → New → Blueprint**, pick `MMP-NZ/ridge2`, and authorise Render's GitHub app when asked. Render reads `render.yaml` and prompts for two values:
   - `SECRET_ENCRYPTION_KEY`: the 64-character value from step 2
   - `NEXT_PUBLIC_APP_URL`: `https://ridge-staging-web.onrender.com`. If Render adds a suffix to the name because it's taken, update this to the real address and redeploy, since Next fixes it at build time.

   The two role passwords are generated by Render and never need to be seen.
4. **Wait for the first deploy.** In the web service's logs, look for `Migrations complete.` from the pre-deploy step. The worker deploys alongside it and can start before migrations finish. That's harmless, because it only uses its own `pgboss` schema until a job arrives, and no job can arrive before the web service is up.
5. **Create your staff login.** Web service → Shell:
   ```bash
   node dist/bootstrap.mjs you@junologic.co.nz "Your Name"
   ```
   It prints a password once. Save it, then log in at `/staff/login`.
6. **Optional: add a fictional demo roofer.** Same shell:
   ```bash
   node dist/seed.mjs
   ```

## Database roles on hosted Postgres

Locally and in the CI `test` job, migrations run as a superuser, and a superuser ignores row-level security. **Render's database owner isn't a superuser**, and it can't be given `BYPASSRLS`. Every tenant table uses `FORCE ROW LEVEL SECURITY`, and every policy is written `TO ridge_app`, so the owner can create and alter tables but is denied every row.

What that means in practice:

- **Migrations work**, because they're schema changes only. Keep it that way: a migration that inserts or updates tenant rows will fail on Render. Do data changes in a script that goes through `withSetupContext`.
- **The owner creates `ridge_app` and `ridge_auth`** (it has `CREATEROLE`), and `migrate.mjs` sets their passwords from `RIDGE_APP_PASSWORD` / `RIDGE_AUTH_PASSWORD` on every deploy.
- **The app never needs a hand-built connection string.** `src/db/urls.ts` builds each role's URL from the owner URL's host plus that role's password.
- **Setup scripts write as `ridge_app` in staff context** (`src/db/setup-context.ts`), so RLS applies to them as it does to a staff request.
- **pg-boss** creates its own `pgboss` schema using the owner connection. That works because the owner owns the database.

## The health check

`/api/health` returns 200 only if:

- `ridge_app` can connect with its password
- photos will persist: `PHOTO_STORE_DIR` is set in production and the app can write to it

If a deploy fails its health check, the web service logs say which one failed (`Health check failed: ...`). The public response never does.

**If the log says `PHOTO_STORE_DIR (/var/data/photos) is not writable`:** the disk has mounted owned by root, while the image runs as uid 1001. Render's docs don't say which owner to expect, which is why this is checked rather than assumed. The fix is an entrypoint that `chown`s `/var/data` and then drops to the `nextjs` user. It isn't built yet, because it isn't known to be needed.

## Staging is safe by construction

- `LOG_ONLY_TRANSPORT=true`: texts and emails are written to the service logs, never sent. Most are sent by the worker, so read booking links there.
- `FAKE_XERO=true`: invoices go to an in-memory Xero that resets when a process restarts. It's fine for walking through the flow, but it isn't a real accounting test.
- Only fictional data.

## Known limits of staging

- **A disk means a brief outage on each deploy.** Render can't keep two instances attached to one disk, so it stops the old one before starting the new one. That's acceptable on staging. Production photos belong in object storage, which removes the disk entirely. The S3 adapter already exists.
- **Fake Xero state lives in memory, separately in the web and worker processes.** A payment recorded in one isn't visible in the other, so the end-to-end commission flow can't be exercised on staging. It's covered by the test suite instead.
- **The database has no public access** (`ipAllowList: []`). Reach it from the web service's Shell. The image has no `psql`, so use the bundled scripts, or add your IP to the allow list temporarily.
